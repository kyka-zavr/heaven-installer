# Heaven Installer — Roadmap

## Идея проекта

Несколько "попутных установщиков", которые вместе закрывают весь путь от голого
LiveCD до готовой десктопной системы, но не пишут велосипед с нуля — под капотом
используют существующие инструменты дистрибутива (archinstall, setup-alpine,
void-installer, ...) как **движок установки**, а не как интерфейс. Интерфейс —
всегда наш, единого стиля.

Разбито на этапы (stages), у каждого своя роль:

- **Stage 1 (этот репозиторий, `heaven-installer.sh` + логика ниже)** — полностью
  CLI, ставит голую базовую систему.
- **Stage 2 (будущее)** — графический, ставит DE/WM, драйверы, софт, темизацию.
  Автозапускается сразу после первой перезагрузки в свежепоставленную систему.

---

## Stage 0 — самый первый шаг: язык и консоль

Ещё до сканирования системы:

1. **Проверка поддержки кириллицы на консоли.** Голый Linux-консоль (tty, не
   GUI-терминал) обычно грузится с дефолтным шрифтом без кириллических глиптов —
   даже если локаль в порядке, русский текст на экране будет "битым"/пустым.
   Нужно:
   - проверить `locale -a` на предмет `ru_RU.UTF-8` (генерировать при
     необходимости через `locale-gen`, если есть `ru_RU.UTF-8` в
     `/etc/locale.gen`);
   - подгрузить юникод-шрифт с поддержкой кириллицы (`setfont`, шрифт из пакета
     `terminus-font`, обычно уже есть на LiveCD);
   - если не получилось гарантировать нормальный рендер — молча падать на EN и
     явно писать об этом (не показывать кашу вместо текста).
2. **Выбор языка (ru/en)** — простой prompt, теперь уже безопасно показывать
   кириллицу (или мы уже знаем, что надо остаться на EN).
3. Дальше весь Heaven Installer (все stage'и) говорит на выбранном языке —
   значение стоит прокидывать через файл/переменную окружения, которую следующий
   stage тоже прочитает (чтобы не спрашивать второй раз).

## Stage 1 — CLI, база системы (текущий репозиторий)

Что уже сделано: баннер, warning+confirm, скан (дистро/boot mode/железо/сеть),
диспатч на `distros/<id>.sh`.

Что добавляется дальше, **все экраны — наши, archinstall только выполняет**:

1. Язык (Stage 0, см. выше)
2. Warning + скан (уже есть)
3. **Разметка диска** — выбор целевого диска, схема (для v1: простая
   "стереть весь диск, авто-layout", без ручного партиционирования — это
   отдельная фича на будущее)
4. **Пользователь** — имя, пароль
5. **Root** — пароль (или сразу решить: root залогинен только через sudo —
   вопрос на будущее обсуждение, стоит зафиксировать явно)
6. **Зеркала** — выбор региона (можно по таймзоне/geoip как подсказка, но
   с возможностью выбрать вручную)
7. **Hostname**, **таймзона** (таймзону можно предлагать по geoip как дефолт)
8. **Доп. пакеты** — небольшой list самим Heaven Installer предложенных
   QoL-пакетов + свободный ввод своих
9. Автоматически подставляется `profile = minimal` (никакого DE/WM — это уже
   зона ответственности Stage 2)
10. Сборка `user_configuration.json` + `user_credentials.json` из ответов
    выше — в формате, который понимает archinstall
11. **Параллельно с установкой** (пока идёт pacstrap) — в фоне подтягиваем/
    кэшируем Stage 2 (сам загрузчик Stage 2, ещё не запускаем)
12. Запуск `archinstall --config ... --creds ... --silent` — без единого
    своего окна, просто ставит систему по конфигу
13. **Автозапуск Stage 2 после первой настоящей загрузки** — в конце Stage 1,
    пока ещё в chroot новой системы, кладём systemd oneshot unit
    (`heaven-stage2.service`, enabled), который при первом реальном
    старте системы сам вытащит и запустит Stage 2, а потом сам себя
    выключит/удалит, чтобы не мешать при следующих загрузках
14. Reboot prompt

## Stage 2 — графический (будущее, только план)

Стартует уже не с LiveCD, а на **свежепоставленной базовой системе** (минимальной,
без DE — см. profile=minimal из Stage 1), автоматически через
`heaven-stage2.service`.

Открытые вопросы, которые надо будет закрыть перед стартом реализации:

- **Чем рисовать GUI до того, как поставлен настоящий DE?** Нужен минимальный
  Xorg/Wayland-сеанс + WM, только чтобы вывести наш инсталлятор на экран.
  Варианты: свой минимальный WM/kiosk-режим (как делает Calamares — Xorg +
  лёгкий WM (openbox и т.п.) + fullscreen-приложение), либо взять готовый
  сверхлёгкий (dwm/sway) — нужно явно выбрать один вариант, не тащить оба.
- **На чём писать сам GUI** — Qt/GTK/что-то web-based (Electron-подобное) —
  нужно решить отдельно, влияет на вес системы и порог входа для разработки.
- Что именно ставит Stage 2: выбор DE/WM для финальной системы, GPU-драйверы,
  наборы приложений, темизация/обои, финальные штрихи аккаунта.
- Самоочистка — Stage 2 должен снести свой bootstrap-service после успешного
  прогона, чтобы не запускаться повторно.

## Архитектурное решение по archinstall (и будущим similar-инструментам)

Не дёргаем внутренние меню инструментов напрямую (ломкий неофициальный API).
Вместо этого: **весь UI — наш**, ответы конвертируются в декларативный
конфиг нужного инструмента (JSON для archinstall, answer-file для
setup-alpine/void-installer, если у них есть подобный unattended-режим — надо
проверять по каждому отдельно), инструмент запускается тихо как движок.
Это даёт: единый визуальный стиль на всех этапах и вообще у всех дистро-бэкендов,
и меньше поломок при апдейтах апстрим-инструментов (конфиг-формат стабильнее
внутренних API).

- Stage 2: Qt/GTK/web, какой минимальный WM/kiosk-режим?
- Как передавать выбор языка (ru/en) между Stage 1 и Stage 2?
